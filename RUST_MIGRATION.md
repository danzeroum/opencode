# opencode — Backend Rust Migration Roadmap

Reference for the incremental migration of the opencode **backend** (core + server +
llm + utilities) from TypeScript/Bun to Rust. Frontends (tui/web/desktop/ui/app)
stay TypeScript. Strategy: **strangler-fig** behind the existing HTTP/OpenAPI contract.

> Status legend: ✅ done · 🟡 in progress · ⬜ not started

> **Branching (decided 2026-06-15):** cutover PRs target a long-lived **`rust-migration`** integration
> branch (NOT `dev`), promoted to `dev` only at deliberate milestones — because pushing to `dev`
> triggers `publish.yml` (release) + `deploy.yml` (deploy). PR #14 (Phase 0/1 + `global.health`) is
> **merged into `rust-migration`**. Merge cadence: ~weekly per cutover PR; CI is the gate.

## Fixed decisions

1. **Strategy:** incremental strangler-fig, behind the same HTTP/OpenAPI contract.
2. **Scope:** entire backend (`core` + `server` + `llm` + utilities). Frontends stay TS.
3. **LLM:** native Rust crates (no TS sidecar). Anthropic/Claude first.
4. **CI:** Rust toolchain + `xtask` (cargo/clippy/rustfmt/nextest), GitHub Actions as executor.

## The seam (how cutover works)

`opencode-bin` runs an **axum** server that fronts a **reverse proxy**. A route table parsed
from `OPENCODE_RUST_ROUTES` (comma-separated group names) decides, per route group, whether
the request is served natively by Rust or proxied to the existing TypeScript server. With an
empty table everything proxies to TS. A group is "cut over" by adding it to the table; rolling
back is removing it. Frontends/SDK keep seeing one unchanged endpoint and one `openapi.json`.

## Workspace layout (`crates/`)

| Crate | Responsibility |
|---|---|
| `opencode-bin` | `opencode` binary: CLI (clap) + boots the server |
| `opencode-server` | axum router, reverse-proxy fallback (seam), OpenAPI (utoipa) |
| `opencode-core` | domain: sessions, events, permissions, agents, projects, jobs |
| `opencode-tools` | tools (bash/read/edit/glob/grep/git/…) + fs/git/search/pty helpers |
| `opencode-llm` | LLM protocol router (ported from `packages/llm`) |
| `opencode-db` | sqlx pool, migration runner, event-store/session-store repos |
| `opencode-config` | JSONC config, schema, catalog (models.dev) merge |
| `opencode-proto` | external HTTP contract types (mirror `packages/sdk/openapi.json`) |
| `opencode-events` | internal event-store contract (versioned events + upcasters) |
| `opencode-effect` | DI/runtime: `AppContext`, error taxonomy, tracing |
| `opencode-plugin` | out-of-process JS plugin host + MCP client (rmcp) |
| `opencode-integration` | github/gitlab/slack adapters |
| `xtask` | build/CI/release/codegen orchestration |

## Key crate choices

tokio · axum 0.8 · utoipa 5 (code-first OpenAPI) · sqlx 0.8 (SQLite) · reqwest 0.12 ·
serde · garde (validation) · schemars (tool JSON Schema) · gix (git) · grep/ignore/globset
(ripgrep libs) · portable-pty · notify · rmcp (MCP) · `aws-sdk-bedrockruntime` (Bedrock) ·
tracing/OpenTelemetry · thiserror/anyhow · clap · insta · cargo-nextest · cargo-zigbuild ·
cargo-dist · cargo-deny. **Out of scope:** tree-sitter (TUI-only).

### Phase 3 — LLM 🟡
- ✅ **Protocol decode pipeline** (PR #25): `opencode-llm` defines the normalized `LlmEvent`/`Usage`/`FinishReason` model + the `Protocol` trait (decode side: `decode_frame` → `step(state) → Vec<LlmEvent>` → `terminal`) + `sse_frames`/`decode_sse` (the `sseFraming` analog). First impl: **anthropic-messages** — folds the Anthropic SSE stream (`message_start`/`content_block_*`/`message_delta`/`message_stop`/`ping`/`error`) into normalized events, threading open blocks + streaming tool-arg buffers + merged usage. **Parity proven network-free** by replaying real `http-recorder` cassettes (`streams-text`, `streams-tool-call`) and asserting the event stream (text, tool-call input `{"city":"Paris"}`, finish reason, token usage).
- ✅ **Request lowering** (`body.from`, PR #26): the `Protocol` trait gains `Body` + `build_body`; `LlmRequest`/`Message`/`ContentPart`/`ToolDefinition`/`ToolChoice`/`Generation` model the normalized request (core subset). anthropic-messages lowers it to the Anthropic body (system text blocks, user/assistant/tool → content blocks incl. `tool_use`/`tool_result`, tools, `tool_choice` auto/any/tool, `max_tokens` default 4096, sampling params). **Parity proven** against the cassettes' recorded `request.body` (text + tool-call). - ✅ **HTTP transport** (PR #27): `opencode-llm::transport::complete` — `build_body` → reqwest `POST` (JSON) → SSE response → `decode_sse` → `Vec<LlmEvent>`; non-2xx → `LlmError::Status { code, retryable, message }` (429/5xx retryable), network → `LlmError::Http`. Tested end-to-end against an in-test **axum** server (happy-path event parity + 429/401 classification) over plain HTTP — no new external crates, no TLS yet. Collect-then-decode (incremental streaming is a refinement).
- ✅ **TLS re-add** (PR #28): `reqwest` now uses **`rustls-tls`** (rustls + ring — owner-approved; no system OpenSSL, best musl/windows-arm cross-compile). `transport::https_client` builds an HTTPS-only client with a timeout for real provider calls. `deny.toml` gained one license (`CDLA-Permissive-2.0`, for webpki-roots' bundled CA set); `ring 0.17.14` reports a clean `Apache-2.0 AND ISC` and needed nothing. The HTTP transport tests are unchanged (TLS only affects `https://`).
- ✅ **Executor** (PR #29): `executor::RetryPolicy` + `execute()` — exponential backoff (`base·2^(n-1)`, capped) + `Retry-After` override + +50%/no-`rand` jitter, retrying retryable `Status` (429/5xx, via the `retry_after` header the transport now parses) and network errors, stopping fast on non-retryable / `max_attempts`. `executor::redact_secrets` masks `sk-ant-…` keys (the transport redacts error bodies). All unit-tested (policy classification/backoff/cap/Retry-After, the retry loop, redaction) + an E2E (axum 429→retry→200). **anthropic-messages is now production-ready: decode + lowering + transport + TLS + executor.**
- ✅ **Second protocol: openai-chat** (PR #30): same `Protocol`/transport/executor scaffolding, validating the abstraction generalizes. Handles the wire differences — system as a `role:"system"` message, string content, `{type:"function",function:{…,parameters}}` tools, `tool_choice` modes, and `tool_calls[].function.arguments` streamed by `index`. OpenAI splits `finish_reason`/`usage` across the last chunks with no terminal event, so the trait gained a defaulted **`on_halt`** flush (Anthropic unaffected). Parity proven against the openai-chat cassettes (request bodies + response streams: text → `"Hello!"` 22/2, tool-call → `get_weather({"city":"Paris"})` 67/5).
- ✅ **Third protocol: gemini** (PR #31): `generateContent` over the same scaffolding. **Finding:** Gemini's `?alt=sse` is **text SSE JSON**, not protobuf/binary (that's Bedrock) — so it reuses `sse_frames`, no binary decoder. Handles `systemInstruction`, `contents`/`parts`, `functionDeclarations`, `functionCallingConfig` modes, atomic `functionCall` parts (args as an object, no id → synthesized), and reasoning-inclusive usage (`candidatesTokenCount + thoughtsTokenCount`); `on_halt` flushes Finish. Parity proven against the gemini cassettes (text 11/18, tool-call `get_weather({"city":"Paris"})` 55/60).
- ✅ **Fourth protocol: bedrock-converse** (PR #32): the **binary** one. New `eventstream` module decodes the AWS `vnd.amazon.eventstream` framing (`[total_len][headers_len][prelude_crc][headers][payload][msg_crc]`, big-endian) and rewraps each `event` frame's JSON payload under its `:event-type` (`{"messageStart":…}`) — so `decode_frame`/`step`/`on_halt` are reused unchanged; `lib.rs` factored a shared `decode_frames` driver behind `decode_sse` (text) and the new `decode_eventstream` (binary). **Finding:** the TS uses only `@smithy/eventstream-codec` (the ~80-line frame codec, hand-rolled here) + `aws4fetch` (a single-file SigV4 signer) — **not** `aws-sdk-bedrockruntime`; so this PR adds **no** AWS deps (and avoids `aws-lc-rs`/the musl/windows-arm cross-compile risk). Converse decode/lowering mirror the structure (content blocks by index, finish split `messageStop`+`metadata` flushed in `on_halt`, `inputTokens`-inclusive usage, `toolConfig`/`toolChoice` auto/any/tool, tool-results as `user` `toolResult` `{json}`/`{text}`). Parity proven against the 3 bedrock cassettes (text `"Hello"` 12/2, tool-call `get_weather({"city":"Paris"})` 419/16, and the 2-turn tool loop). **Deferred to a focused follow-up:** SigV4 request signing + the live binary transport (decode is transport-agnostic — fed `decode_eventstream` here, live frames later) and CRC validation; recommend hand-rolled SigV4 (RustCrypto `sha2`+`hmac`, pure-Rust) or the `aws-sigv4` crate (ring-based, no new C dep) over the full SDK.
- ✅ **Fifth protocol: openai-responses** (PR #33): the **Responses API** (distinct from openai-chat's Chat Completions). Text SSE → reuses `sse_frames`/`decode_sse`. The shape differs: the request is an `input` array of typed items (system as string content, user/assistant as `input_text`/`output_text`), tools are flat (`{type:"function",name,…}`), and tool calls/results are **top-level** `function_call`/`function_call_output` items (not message content); the stream is typed lifecycle events (`response.output_item.{added,done}`, `response.output_text.delta`, `response.function_call_arguments.delta`, `response.completed`). Tool-call id is the `call_…` id (what results reference), tracked separately from the `fc_…` stream item id; the terminal `Finish` is emitted on `response.completed` (carries status + usage, reasoning-inclusive `output_tokens`); finish reason derives from `incomplete_details.reason` + whether a tool was called. Parity proven against the gpt-5.5 cassettes (text `"Hello!"` 20/18, tool-call `get_weather({"city":"Paris"})` 61/18, 2-turn loop). No new deps. Reasoning-summary streaming / media / option knobs deferred. **Phase 3 protocol portfolio complete (5/5): anthropic-messages, openai-chat, gemini, bedrock-converse, openai-responses.**
- ⬜ Remaining Phase 3 follow-up: the deferred Bedrock SigV4 + live binary transport (every other protocol has a transport; bedrock's was split out). No public cutover (the runner consumes these; Phase 4).

### Phase 4 — Session runner 🟡
- ✅ **Control-flow spike** (PR #24, pure logic — no IO/cutover): `opencode-core::runner` proves the `session/runner/llm.ts` control flow maps to panic-free Rust. `die(TurnTransitionError)`/`catchDefect` → `TurnTransition` (`RebuildPreparedTurn{promotion}` / `ContinueAfterOverflowCompaction`) returned as `Err` + the `run_turn` restart driver (flips `OverflowRecovery` `Enabled→Disabled`; a second overflow is `DoubleOverflow`); `needsContinuation` → `TurnOutcome::{Continue,Done}`; the outer continuation loop → `run_session` (step-limited); `FiberSet` + `raceFirst(join,awaitEmpty)` → `ToolExecutor` (over `tokio::task::JoinSet`) with `drain` (fail-fast vs all-settled) + `cancel_all`. 14 unit tests exercise every transition + tool race/timeout/cancel.
- ✅ **Minimal session runner** (PR #34, first end-to-end slice — no cutover): `opencode-core::session` wires the spike's primitives into a real async turn loop over the LLM + tools. Two seams: `LlmEngine` (one provider round-trip → normalized `LlmEvent`s; real impl wraps `transport::complete`, tests script it) and `ToolBox` (execute a tool by name; tool-level errors are fed back to the model, not fatal). The loop (async analog of `run_session`) lowers the conversation to an `LlmRequest`, folds the turn's events into the assistant message (text + tool calls + summed usage), runs tool calls concurrently on the spike's `ToolExecutor` (`drain`/`cancel_all`), feeds results back as a `tool` message, and continues until a turn issues no tool calls (`Done`) or the step limit is hit. Per the plan's "start minimal" guidance: **one provider (anthropic), one tool, no plugins/permissions**. Proven by 5 tests incl. a real **end-to-end** run over the HTTP transport (in-test axum server streams a tool call then a text answer → the decoded tool call drives a real `ToolBox` execution fed back into turn 2). Deferred: overflow recovery (the `run_turn` transitions — needs compaction), durable persistence + event-bus production, permissions/question, and the multi-provider/registry wiring.
- ✅ **Durable persistence** (PR #35, no cutover): the runner becomes a real event **producer**. A `SessionSink` seam decouples the turn loop from where events go — the runner streams each turn's events as **one atomic batch** (`run_with_sink`; `run` stays the ephemeral convenience delegating to a `NoopSink`). `EventStoreSink` appends each batch to the `opencode-db` `EventStore` under the session's aggregate id, advancing the optimistic-concurrency head across batches (a concurrent-writer conflict surfaces as a `RunError`; steering/compaction-restart handling is a later increment). Event vocabulary (versioned `name.N`): `message.assistant.1` (text + tool calls), `message.tool_results.1`, `session.finished.1` (outcome + steps + summed usage — the run "snapshot"). 3 new tests: a 2-turn loop persists `[assistant, tool_results, assistant, finished]` with monotonic seqs + correct payloads, appends continue an existing log (head seeding), and a concurrent write surfaces a conflict. Deferred: event-bus production (the SSE consumer), `replay`/projection rebuild, overflow recovery via the `run_turn` transitions.
- ✅ **Event-bus production** (PR #36, no cutover): the runner now **announces** events live, not just persists them — completing the producer story. `BusSink` publishes each event to the in-process `EventBus` (scoped to the session aggregate; fire-and-forget, never aborts a run). `FanOutSink<Primary, Secondary>` composes sinks "**persist then announce**": an `EventStoreSink` primary (authoritative — its failure aborts the run) followed by a best-effort `BusSink` secondary (its failure is swallowed), so nothing is announced that failed to persist and a stalled bus never blocks the runner. 3 new tests: fan-out reaches both store + bus (same kinds, aggregate-scoped, in order); a store conflict aborts before any bus publish; a failing secondary is soft (the primary still commits). No new deps (`EventBus` already lived in `opencode-effect`). The internal `/_rust/event` SSE route already streams the bus; the **public** `/event` cutover is the route-cutover step below.
- ✅ **Permission / question gating** (PR #37, no cutover): the first business-logic guard — tools only run with permission. A `PermissionGate` seam is consulted **before** each tool call (`run_gated`; `run_with_sink` delegates with the default `AllowAll`, so existing behavior is unchanged). `Decision::Allow` runs the tool; `Decision::Deny(reason)` skips it and feeds `"Permission denied: {reason}"` back to the model as the tool result (recording a `permission.denied` event); `Decision::Ask` **suspends** the run — records a `permission.requested` event and returns the new `SessionOutcome::AwaitingPermission { steps }` (the resume path, via the steering inbox, is a later increment). Decisions are per-call (allow/deny mix in one turn) and fully audited through the sink. `execute_tools` was refactored to `run_tools` (returns id→output) so allowed results and denials merge in call order. 3 new tests: allow runs the tool, deny skips + audits + feeds back the denial, ask suspends (turn 1 never consumed) + records the request. New event kinds: `permission.denied.1`, `permission.requested.1`. No new deps.
- ✅ **Native tools** (PR #38, no cutover): the first **real** runner collaborator — a `NativeToolBox` implementing the `ToolBox` seam by dispatching the agent's tool calls (`read`/`write`/`edit`/`ls`/`glob`/`grep`/`bash`) to the ported `opencode-tools` helpers, rooted at a working directory, with the matching `ToolDefinition`s (JSON schemas) the model is offered via `tool_definitions()`. Sync fs/search helpers run on `spawn_blocking`; `bash` is async (`run_shell`). Authorization stays the `PermissionGate`'s job (this only executes). 8 tests: each tool against a temp dir (read incl. line-range, write round-trip, unique-edit, ls/glob/grep over a tree, bash in the root), unknown-tool/bad-input/missing-file errors, the definitions list, and a **runner-integration** test where a scripted tool call drives a real `read` whose file content is fed back into the loop. `opencode-core` gains `opencode-tools`/`serde` deps (+ `tempfile` dev-dep), all already in the workspace tree. **The cross-process `/event` blocker:** during coexistence the public `/event` stays proxied to TS — the Rust bus has no producers for live sessions until the runner is wired into the server's session-execution path (the `NativeToolBox` is the first brick of that wiring).
- ⬜ Continue wiring the runner toward the server: a config/credential-driven `LlmEngine` (real provider selection) + the `AppContext`-constructed runner invoked on a gated session-execution path; the **resume** path for `AwaitingPermission` (+ `session_input` steering inbox); projected history rebuild + `replay`; overflow/compaction via the `run_turn` transitions. **Only then** can `/event` (and session writes) cut over. Plus a real DB-backed `PermissionGate` and the deferred Bedrock SigV4/live transport (Phase 3 follow-up).
- ⬜ Cutover: `session`, `message`, `permission`, `question`, and finally the real `/event` (Rust now produces events)
